# openwork Stack — Base Scaffold Plan

**Goal:** Scaffold the functional base of the `openwork` stack (openwork-host
server + source-built selfhost web UI + volumes + env layering), mirroring the
sibling `opencode` stack's structure exactly, ready for the stack-test Stage A
gate.

**Contract:** `stacks/self-hosting/ai-services/automation/openwork/DEPLOYMENT.md`
(binding) + `UPSTREAM.md` (pins). Structure mirror:
`stacks/self-hosting/ai-services/automation/opencode/`.

**Planning mode:** per user instruction, the planner writes NO compose or
Dockerfile content. Each micro-task is a spec: exact path, purpose,
constraints, verify step. Implementers author the file contents following the
cited sibling reference files.

## Naming resolution (binding)

- **Server image dir:** DEPLOYMENT.md (the contract) names the product part
  `openwork-host` and its image `app/images/openwork-host/Dockerfile`. The
  earlier instruction's `openwork-server` path is superseded. **Use
  `app/images/openwork-host/Dockerfile`.** The compose service itself is
  `openwork` (main product service = exactly the stack name; `-app` banned).
- **Web image dir:** `app/images/openwork-web/Dockerfile` (per DEPLOYMENT.md).
- **Volumes:** `openwork-data` (→ `/data`), `openwork-workspace` (→
  `/workspace`). **Network:** `openwork-network`. `COMPOSE_PROJECT_NAME=openwork-stack`.

## Sibling file-naming set (copy exactly)

The `opencode` stack uses `docker-compose.yml` (NOT `compose.yaml`) inside
`app/components/` (NOT flat `app/`), with `sb`/stackbuilder builds. The exact
tree to mirror:

```
app/
├── stackbuilder.toml
├── README.md
├── build/{forwarding,letsencrypt,step-ca}/        # generated by sb build (gitignored except plugins)
├── components/
│   ├── base/{docker-compose.yml, .env.example}
│   ├── environments/{forwarding,letsencrypt,step-ca}/{docker-compose.yml, .env.example}
│   └── extensions/{repo-sync,repo-local,step-ca-trust}/{docker-compose.yml, .env.example}
```

openwork deviations from the sibling (deliberate, recorded):

1. **`app/images/{openwork-host,openwork-web}/Dockerfile`** — new dirs; opencode
   uses a published image, openwork has none (§19 source-built, empty context,
   self-contained clone/download at pinned refs).
2. **Extension `model-keys`** added (core, required-for-gate per DEPLOYMENT.md;
   included in EVERY combo).
3. **No `components/base/plugins/` + no base `entrypoint.sh`** — opencode's
   plugin-injection layer targets its own serve entrypoint; openwork-server
   manages its opencode sidecars itself and no plugin surface is verified
   upstream. Flagged as possible follow-up, not scaffold scope.
4. **`modules/ssl-automation/` submodules** — same two managers as opencode
   (letsencrypt-manager, step-ca-manager), same URLs from opencode's
   `.gitmodules`.

## Key design decisions (HOW, made by planner)

- **D1 — Prebuilt images, no `build:` in compose.** Both services reference
  `image: ${IMAGE:-localhost/<image>:<tag>}` (host: `localhost/openwork-host:0.18.4`,
  web: `localhost/openwork-web:0.18.4`); images are built from the §19
  Dockerfiles with empty context. No `dockerfile_inline` FROM-layer (that
  pattern needs a published base image).
- **D2 — Web URL at runtime, not baked.** `VITE_OPENWORK_URL` is
  environment-dependent → overlays only (§7). The web image builds the bundle
  with a placeholder (e.g. `__OPENWORK_URL__`) and a tiny entrypoint
  substitutes `${OPENWORK_PUBLIC_URL}` into the served static files at
  container start. Implementer must verify against upstream `apps/app`
  selfhost output (DEPLOYMENT.md hypothesis #2); if the bundle offers a
  runtime-config mechanism, prefer it. Fallback rejected: baking the URL per
  environment breaks image/environment separation.
- **D3 — Two public origins in TLS modes.** nginx-proxy is vhost-based:
  `openwork-web` gets `VIRTUAL_HOST` (UI), `openwork` gets a second vhost
  (API). Overlays set `OPENWORK_PUBLIC_URL=https://<api-vhost>` (web runtime
  substitution) and `OPENWORK_CORS_ORIGINS=https://<ui-vhost>` (server
  `--cors`). Forwarding mode publishes both container ports directly.
- **D4 — `OPENWORK_TOKEN` in base.** Core auth → base compose
  `${OPENWORK_TOKEN:?}` on the `openwork` service; placeholder-only in base
  `.env.example`. The UI collects the token from the user (product behavior).
- **D5 — model-keys fragment in every combo.** `stackbuilder.toml` combos:
  `entire = ["model-keys", "repo-sync"]`,
  `entire-trust = ["model-keys", "repo-sync", "step-ca-trust"]`.
  `repo-local` is the swap-in alternative to `repo-sync` (never both), same
  as opencode.
- **D6 — Build resource caps (5GB host).** The web image's build stage caps
  Node/pnpm: `NODE_OPTIONS=--max-old-space-size=2048`, pnpm
  `--child-concurrency=2` / network-concurrency limits, no parallel vite
  workers beyond default. Host safety rules apply: if the build OOMs, report
  and stop — never touch host swap/devices.
- **D7 — Healthchecks.** `openwork`: HTTP GET on
  `http://127.0.0.1:${OPENWORK_PORT:-8787}` (pick an unauthenticated upstream
  endpoint; verify against the npm bundle). `openwork-web`: nginx default
  stub or a static-file GET.

## Batch 4 — Extensions (one per implementation cycle, each gated)

User-confirmed extension order (binding): 1) `openwork-inference` →
2) `review` → 3) `otel-lgtm` → 4) TLS environment gate (letsencrypt or
step-ca). **One extension per implementation cycle** — never start the next
extension before the current one's stack-test gate passes and its
README/DEPLOYMENT.md status is flipped. Each cycle ends with a gate run under
the `stack-test` skill. All gates are **key-free** (no real provider key is
available): token positive/negative checks, route health, persistence after
restart, and — for otel-lgtm — OTLP trace emission WITHOUT model inference.
Server routes are UNPREFIXED (PITFALLS P-035): use `/status`, `/whoami`,
`/workspaces`, `/tokens` — never `/api/*`.

Shared rules for every extension task group:

- Fragments live in `app/components/extensions/<name>/docker-compose.yml` +
  `.env.example`, mirroring the shape of `app/components/extensions/model-keys/`
  (service-scoped env passthrough, `${VAR:-}` everywhere, extension vars ONLY
  in the fragment's `.env.example`).
- Every new image follows the `source-image` skill: `app/images/<image>/Dockerfile`,
  pinned upstream tag/commit, empty build context, never vendor upstream source;
  compose references it via `image: ${IMAGE:-localhost/<image>:<tag>}`.
